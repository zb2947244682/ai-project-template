# Project Pilot — AI 驱动的大型项目全流程开发技能

## 核心理念

AI 在开发大型项目时最常见的失败模式是「过早宣布完工」——因为缺乏全局视图，AI 会在完成几个模块后就认为项目已经结束。本技能通过建立一套完整的文档体系来解决这个问题：

1. **文档是 AI 的外部记忆** — AI 的上下文窗口有限，文档让它在任何时刻都能对照全局进度
2. **文档是完成度的客观标准** — 只有任务清单全部打勾、测试用例全部通过，项目才算完成
3. **文档是跨会话的桥梁** — 每次新会话都能通过文档无缝衔接上次的进度

## 阶段一：需求采集（文档驱动的迭代问答）

这是整个流程中最关键的阶段。AI 通过创建「问答文档」向用户提问，用户在文档中填写答案后告知 AI，AI 阅读答案后继续追问，直到无法再提出新问题为止。

### 1.1 问答流程规则

**核心原则：问到无问题可问为止，不设轮次上限。**

具体流程：

```
第 1 轮：创建 QA-R01-项目愿景.md    → 覆盖项目的宏观定义
第 2 轮：创建 QA-R02-用户与场景.md   → 覆盖用户画像和使用场景
第 3 轮：创建 QA-R03-功能细节.md    → 覆盖每个功能的详细规格
第 4 轮：创建 QA-R04-技术约束.md    → 覆盖技术选型和限制
第 5 轮：创建 QA-R05-数据与安全.md   → 覆盖数据模型和安全需求
第 6 轮：创建 QA-R06-追问与补充.md   → 基于前 5 轮的答案追问细节
第 N 轮：创建 QA-R{N}-深入追问.md   → 持续追问，直到再无疑问
```

每轮问答文档被用户填写完毕后，AI 要做两件事：
1. 仔细阅读用户的回答，提取所有有价值的信息
2. 基于新获得的信息，判断是否还有未覆盖的细节需要追问

**停止条件：当 AI 判断以下所有领域都已被充分覆盖时，才可以结束问答阶段：**
- 产品定位与目标用户
- 所有功能的详细规格（包括边界情况和异常处理）
- 用户交互流程（每个页面/屏幕的具体行为）
- 数据模型（每个实体的字段、类型、关系）
- 技术栈和架构约束
- 第三方集成需求
- 非功能性需求（性能、安全、可访问性）
- 部署和运维需求
- 项目范围边界（明确不做什么）

### 1.2 问答文档的格式规范

每份问答文档必须遵循以下格式，让用户能清晰地填写：

```markdown
# 问答文档 - 第 {N} 轮：{主题}

> 请在每个问题下方的「您的回答」区域填写。
> 如果某个问题不适用，请填写"N/A"并简要说明原因。
> 如果某个问题您还没想好，请填写"待定"，我会在后续轮次中再次确认。
> 填写完毕后，请告诉我"已填写完毕"。

---

## Q1: {问题标题}

**背景**：{为什么问这个问题，这个信息将用于什么文档}

**问题**：{具体的问题描述}

**示例参考**：{给出 1-2 个示例答案，帮助用户理解期望的回答粒度}

**您的回答**：

{用户在这里填写}

---

## Q2: {问题标题}
...（同上格式）
```

### 1.3 各轮问答的覆盖范围

以下是每一轮问答应该覆盖的主题指南。AI 应该根据项目的具体类型灵活调整，但不能遗漏关键领域。

#### 第 1 轮：项目愿景与边界

必须覆盖的问题方向：
- 项目要解决的核心问题是什么？用一句话描述
- 目标用户是谁？列出所有用户角色
- 与市面上现有的同类产品相比，核心差异是什么？
- 项目的 MVP（最小可行产品）包含哪些功能？
- 明确不做什么？列出范围外的功能
- 预期的上线时间节点
- 是否有预算或资源限制

#### 第 2 轮：用户画像与使用场景

必须覆盖的问题方向：
- 每个用户角色的典型使用场景（用故事化描述）
- 用户的技术水平和使用习惯
- 用户最常使用的设备和平台
- 用户最关心的体验指标（速度？易用性？美观？）
- 用户的操作频率（日活/周活/月活）
- 是否有无障碍访问需求

#### 第 3 轮：功能详细规格

必须覆盖的问题方向（针对 MVP 中的每个功能）：
- 功能的完整用户操作流程（step by step）
- 每一步的输入、输出、校验规则
- 异常情况的处理方式（网络失败、输入非法、权限不足等）
- 功能之间的依赖关系
- 是否有实时性要求（如即时消息、实时协作）
- 是否需要离线支持

#### 第 4 轮：技术约束与选型

必须覆盖的问题方向：
- 前端技术偏好（React / Vue / 原生等）
- 后端技术偏好（Node / Python / Go / Java 等）
- 数据库偏好（PostgreSQL / MySQL / MongoDB 等）
- 是否需要使用特定的云服务商
- 是否有现有的代码库或系统需要集成
- 是否需要 CI/CD 流水线
- 代码仓库管理方式（monorepo / multi-repo）
- 是否有团队成员协作开发（影响编码规范的严格程度）

#### 第 5 轮：数据模型与安全

必须覆盖的问题方向：
- 系统中有哪些核心数据实体？
- 每个实体包含哪些字段？（名称、类型、是否必填、默认值）
- 实体之间的关系（一对一/一对多/多对多）
- 数据的生命周期（创建→使用→归档→删除）
- 是否有数据迁移需求
- 认证方式（用户名密码 / OAuth / SSO 等）
- 授权模型（RBAC / ABAC / 简单权限）
- 敏感数据的加密存储需求
- 是否需要符合特定法规（GDPR / HIPAA 等）
- 日志和审计需求

#### 第 6 轮及后续：追问与深入

基于前面所有轮次的答案，AI 应该：
- 发现答案之间的矛盾或模糊之处，要求澄清
- 针对用户说"待定"的问题重新提问
- 针对复杂功能追问更多边界情况
- 确认 UI/UX 的关键决策（如导航结构、核心页面布局）
- 确认第三方服务的具体选择（如支付网关、邮件服务、文件存储）
- 确认部署环境和运维策略
- 确认错误处理和监控策略

### 1.4 问答阶段的行为准则

- **每轮问题数量**：每份问答文档包含 8-15 个问题，不要一次问太多导致用户疲惫
- **问题的深度**：从宏观到微观逐轮深入，不要在第一轮就追问实现细节
- **提供示例**：每个问题都要提供示例答案，降低用户的思考负担
- **解释目的**：每个问题都要说明这个信息将用于哪份文档的哪个部分
- **尊重"待定"**：如果用户说"待定"，在后续轮次中再次询问，但不要强迫
- **主动建议**：如果 AI 基于经验认为某个方案更优，应在问题中给出建议
- **不要假设**：不要替用户做任何决定，所有设计决策都需要用户确认

function login(email, password):
    user = userRepository.findByEmail(email)
    if user is null:
        throw NotFoundError("用户不存在")
    if not verifyPassword(password, user.hashedPassword):
        throw UnauthorizedError("密码错误")
    accessToken = generateJWT(user.id, expiresIn="15m")
    refreshToken = generateJWT(user.id, expiresIn="7d")
    store refreshToken in database
    return { accessToken, refreshToken, user }
```

### 3.1 每个任务的执行流程

```

### 3.2 开发阶段的行为准则

- **一次只做一个任务**：不要跳跃式开发，严格按照任务清单顺序
- **不要偷偷做额外工作**：如果发现需要新任务，先添加到任务清单，不要直接做
- **每完成一个任务必须更新两份文档**：任务清单 + 上下文交接文档
- **遇到阻塞立即报告**：如果某个任务因为外部原因无法完成，标记为阻塞并说明原因
- **代码必须通过测试才算完成**：仅仅"写完了"不算完成，必须有测试验证
- **不要修改已确认的接口契约**：如果必须修改，需要先说明影响范围并获得确认

每次新会话开始时，AI 必须按以下顺序操作：

```
1. 阅读上下文交接文档（07-SESSION-CONTEXT），了解当前进度
2. 阅读任务清单（03-TASKS），确认下一个待做任务
3. 阅读该任务相关的 PRD 章节，确认功能需求
4. 阅读接口契约文档中相关的接口定义
5. 阅读编码规范文档（每次都要重读，确保风格一致）
6. 开始执行任务
```

## 阶段四：验收与交付

### 4.1 验收流程

```
1. 所有任务清单中的任务全部标记为 [x]
2. 所有测试用例全部通过
3. 逐个功能按照 PRD 的验收标准检查
4. 检查非功能性需求是否满足
5. 更新所有文档到最终状态
6. 生成最终的项目交付清单
```

### 4.2 交付清单

```markdown
# 项目交付清单

## 代码交付
- [ ] 源代码完整且可编译
- [ ] 所有依赖已记录在 package.json
- [ ] .env.example 包含所有必要的环境变量
- [ ] README.md 包含完整的启动指南

## 文档交付
- [ ] PRD 已更新到最终版本
- [ ] 技术架构文档反映实际实现
- [ ] 任务清单所有任务已完成
- [ ] 接口契约文档与实际 API 一致
- [ ] 测试计划文档与实际测试一致

## 质量保证
- [ ] 所有单元测试通过
- [ ] 所有集成测试通过
- [ ] 代码风格检查通过
- [ ] 无已知严重 Bug
```

## 关键行为约束（AI 必须遵守）

1. **永远不要自行宣布项目完成。** 只有当任务清单中所有任务标记为 [x]，且所有测试通过时，才可以说项目完成。
2. **永远不要跳过问答阶段。** 即使用户说"你直接做吧"，也要至少完成 3 轮问答以收集基本需求。
3. **永远不要在没有文档的情况下开始写代码。** 先生成文档，文档确认后才能开始开发。
4. **永远不要修改接口契约而不通知用户。** 接口变更会影响多个模块，必须先评估影响。
5. **每次会话结束前必须更新上下文交接文档。** 这是跨会话连续性的生命线。
6. **遇到不确定的决策，问用户而不是自己猜。** 宁可多问一次，也不要猜错后返工。
7. **问答文档中的每个问题都要提供示例答案。** 降低用户的思考成本。
8. **任务粒度要足够小。** 每个任务应该在单次会话中可完成，产出不超过 300 行代码。
9. **文档要足够详细。** 最终的 7 份文档合计应在 1000 行以上，包含伪代码和具体的数据结构定义。
10. **尊重用户的每一个回答。** 不要忽略用户在问答中提到的任何细节，每个细节都要反映到某份文档中。
